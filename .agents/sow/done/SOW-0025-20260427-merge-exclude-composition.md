### Design facts and constraints

- `cymru_unassigned = fullbogons - bogons` is semantically different from `anonymous`.
- Exclusion inputs must be treated as hard composition dependencies. If `bogons` is missing, publishing `fullbogons` alone under the name `cymru_unassigned` would silently broaden the feed and violate the name.
- `DerivedFrom` is overloaded today: dependency graph, lineage display, cycle detection, merge input count ordering, relatedness classification, enable propagation. Adding signed composition without separating these meanings risks confusing UI/API and comparison semantics.
- Backward compatibility requires all existing `sources:`-only merges to load and behave exactly as before.
- Public `/compose` already has tested include/exclude logic, so configured merge subtraction should reuse the same set algebra pattern rather than inventing another algorithm.

### Risk review

- Correctness risk: missing subtractive input could create a broader feed than configured. Mitigation: fail composition if any eligible configured exclude lacks a body.
- API/UI risk: existing `merge_excluded` field already means health/availability-excluded positive inputs. Reusing it for subtractive inputs would be ambiguous. Mitigation: add/rename fields carefully, e.g. `merge_subtracted` for configured subtractive inputs and keep `merge_excluded` for skipped configured inputs.
- Dependency risk: if subtractive parents are not in the dependency graph, updates to `bogons` will not trigger recomposition of `cymru_unassigned`. Mitigation: include both positive and subtractive parents in dependency traversal, but store signed lists separately.
- Comparison risk: treating subtractive parents as ordinary positive ancestry may mark more comparisons as related and hide useful overlap rows. Mitigation: decide whether `DerivedFrom` means all dependencies or only positive ancestry; recommendation below separates `MergeInputs`, `MergeExcludes`, and `DerivedFrom` semantics.
- Ordering risk: current merge ordering uses `len(DerivedFrom)`. If `DerivedFrom` includes excludes, tie-break ordering changes slightly. This is probably acceptable but should be explicit and tested.
- Naming risk: `exclude` can be confused with health-policy exclusion. Mitigation: curator YAML uses `exclude:` because it matches public `/compose`, while runtime/admin fields use `subtracted` for the configured subtractive role.

## Implications and decisions

### Decision 1: YAML field name

Evidence:

- Existing public API parameter is `exclude`. Evidence: `pkg/engine/public.go:273`.
- Existing merge YAML uses `sources`. Evidence: `pkg/config/config.go:398`.

Options:

A. `exclude:`
- Pros: matches public `/compose?exclude=...`; short; clear in `sources + exclude` form.
- Cons: singular word for a list; can be confused with health-policy exclusion unless docs are precise.
- Implications: catalog examples are easy to read.
- Risks: admin/runtime naming must avoid overloading `merge_excluded`.

B. `excludes:`
- Pros: plural list name.
- Cons: diverges from public API; slightly less natural beside `sources`.
- Implications: less accidental collision with existing query parameter but more naming inconsistency.
- Risks: future docs must explain why config and API differ.

Recommendation: A, `exclude:`.

User decision:

- 2026-04-27: Costa approved standard configured merge exclusion semantics. Field name not explicitly stated by Costa; recommendation is `exclude:` because it aligns with public compose.

### Decision 2: Composition semantics

Evidence:

- User stated: "A+B+C-D-E (first the merges, then the excludes)".
- Public compose already performs include union first, then exclusions. Evidence: `pkg/engine/public.go:291-328`.

Options:

A. `union(sources) - union(exclude)`.
- Pros: exactly matches user request; easy to reason about; exclusions are order-independent.
- Cons: requires loading exclude sets in merge composition.
- Implications: `A+B-C-D` equals `(A union B) minus (C union D)`.
- Risks: broad feeds if missing excludes are ignored; must fail instead.

B. Sequential left-to-right expression parser.
- Pros: future expressive syntax.
- Cons: more complex; harder to validate; unnecessary for current need.
- Implications: introduces operator precedence questions and more user-facing syntax.
- Risks: higher maintenance burden and more edge cases.

Recommendation: A.

User decision:

- 2026-04-27: Costa explicitly approved "first the merges, then the excludes".

### Decision 3: Missing exclude behavior

Evidence:

- Current merge contract fails when any currently eligible input lacks a durable local feed body. Evidence: `.agents/sow/specs/config.md:376-377`.
- `cymru_unassigned` would be dangerously wrong if `bogons` were unavailable and output became all `fullbogons`.

Options:

A. Missing eligible exclude fails composition.
- Pros: correctness-preserving; keeps previous good output instead of publishing a broader feed.
- Cons: stricter than "best effort"; may delay first publication until both feeds are available.
- Implications: subtractive feeds have predictable meaning.
- Risks: first-run availability depends on all configured signed inputs.

B. Missing eligible exclude is ignored.
- Pros: more likely to produce an output on first run.
- Cons: can silently publish a feed broader than intended.
- Implications: `cymru_unassigned` could temporarily equal `fullbogons`.
- Risks: unacceptable semantic drift for security lists.

Recommendation: A.

User decision:

- 2026-04-27: Costa approved A.
- Implementation note: kept the existing `merge_included` field for additive
  applied inputs, added `merge_subtracted` for configured subtractive applied
  inputs, and preserved `merge_excluded` for disabled/archived/unmaintained or
  missing configured inputs.

### Decision 4: Runtime metadata model

Evidence:

- `merge_excluded` currently means configured positive inputs skipped because disabled/archived/unmaintained/missing. Evidence: `pkg/engine/merge_inputs.go:10-23`, `pkg/web/admin.go:186-190`, `pkg/engine/output.go:80-85`.

Options:

A. Add signed role fields: `merge_inputs`, `merge_subtracted`, and keep `merge_excluded` for skipped configured inputs.
- Pros: clear; avoids reusing "excluded" for two meanings.
- Cons: API shape grows.
- Implications: admin/UI can render both configured equation and runtime skipped inputs.
- Risks: need compatibility handling so existing consumers of `merge_included`/`merge_excluded` do not break.

B. Reuse `merge_included` / `merge_excluded` for positive/subtractive roles.
- Pros: fewer fields.
- Cons: breaks current meaning of `merge_excluded`.
- Implications: ambiguous whether an item was configured as subtractive or skipped due to health.
- Risks: misleading admin/API output.

Recommendation: A.

User decision:

- 2026-04-27: Costa approved A.

## Outcome

Implemented signed configured merge composition. Authored merge YAML can now
declare additive inputs with `sources:` and subtractive inputs with `exclude:`.
Runtime composition publishes `union(sources) - union(exclude)` and treats any
eligible configured subtractive input that cannot be used as a failure.

`cymru_unassigned` is now a configured Team Cymru merge:

- `sources: [fullbogons]`
- `exclude: [bogons]`
- `use: [bogons]`
- category `special_use`
- output `netset`

Public/admin metadata now exposes signed merge roles clearly with
`merge_included`, `merge_subtracted`, and health-policy `merge_excluded`.
Bogon comparison provider artifacts include `cymru_unassigned` through the
normal processing/reprocess path, not public request handlers.

Public raw-body routes now enforce raw redistribution policy and stream exact
published `.ipset`/`.netset` files. Public artifact routes for feed-scoped and
country/ASN entity data serve the configured published tree or return missing;
they do not live-build those artifacts.

The development service was rebuilt and restarted through `./install.sh`, a
live reprocess regenerated stale metadata, and admin integrity is clean.

## Lessons extracted

- Specs: signed merge composition belongs in the config/feed/pipeline/admin
  contracts, not just code comments.
- Specs: generated artifact ownership must include producer, refresh/repair,
  and serving path; otherwise request-time fallback can slip back in through
  adjacent routes.
- Project coding skill: future merge work must preserve both the full
  dependency graph and the signed include/exclude roles; `DerivedFrom` and
  `merge_excluded` are not enough to encode the equation.
- Project reviewing skill: raw-body policy must be reviewed across every public
  body route together, including compose and compatibility downloads, not only
  feed metadata.
- Project testing skill: stale published artifacts need tests. Fresh generation
  tests are insufficient when the service can keep serving old public JSON.
- Validation lesson: installed service smoke must check live metadata shape,
  raw-body policy, provider artifacts, and admin integrity, not only that the
  feed exists.

## Regression

### Regression 1 — 2026-04-27

**Reported by:** Costa and independent reviewer pass.

**Symptom:** `cymru_unassigned` was implemented as a first-class feed but was
not included in the bogon comparison provider list. Reviewer pass also found
that subtractive parents could be skipped as ordinary health-excluded inputs,
which could silently broaden a signed merge.

**Detection:** Costa asked how the bogon comparison list is derived and whether
adding `cymru_unassigned` would regenerate artifacts or accidentally happen at
request time. External reviewers inspected the same SOW and current diff.

**Original Outcome (for reference):** signed configured merge composition shipped
for `union(sources) - union(exclude)` and `cymru_unassigned = fullbogons -
bogons`.

**Why the original Validation missed this:** validation proved the merge feed
itself and happy-path subtraction, but did not assert provider-role propagation
for merge-derived feeds, did not assert generated bogon artifact coverage for
the new provider, and covered only missing subtractive bodies, not disabled or
archived subtractive parents.

**Fix scope:** add merge `use:` role propagation, mark `cymru_unassigned` as a
bogon provider, prove generated artifact coverage/serving discipline, and make
configured subtractive inputs strict so disabled/archived/unmaintained/missing
subtractive parents fail rather than broaden the merge.

**Regression validation:** captured in the Validation section above. The
specific regression guards are `TestCatalogCymruUnassignedMergeSubtractsBogons`,
`TestBogonProvidersIncludesMergeDerivedProvider`,
`TestWriteBogonComparisonFilesIncludesMergeDerivedProvider`,
`TestExpectedSecondaryFilesIncludesMergeBogonProviders`, the strict
subtractive dependency tests in `pkg/engine/feed_body_stage_test.go`, and the
published-artifact serving tests in `pkg/web`.

### Regression 2 — 2026-04-27

**Reported by:** repeated external reviewer pass.

**Symptom:** after the first regression fix, reviewers found remaining fragile
public-serving edges: global country/ASN API routes could still live-build or

### Regression 4 — 2026-04-27

**Reported by:** final external reviewer pass and live service smoke.

**Symptom:** newly generated metadata was sanitized, but already-published
non-redistributable metadata artifacts could keep exposing raw/source fields
until a reprocess happened. That made the fix incomplete for a running service
with stale public artifacts.

**Detection:** final external review flagged the stale-artifact risk. Live

**Fix scope:** clear raw/source fields when generating metadata for

**Regression validation:** captured in the Validation section above. The
