# SOW-0013 | 2026-04-26 | public-mcp-server

## Status

Status: completed

## Requirements

Given update-ipsets should become a public Streamable HTTP MCP server, when this SOW is complete, then `/mcp` must expose an MCP-compliant public endpoint.

Given the exposed MCP capabilities affect security and server load, when planning starts, then Costa must approve the tools, resources, prompts, authentication/rate-limit model, and admin exclusion rules.

Given this endpoint is public, when implemented, then it must validate transport/security assumptions and must not expose admin operations.

Given MCP is a parallel public interface to the website, when this SOW is
complete, then MCP tools/resources must expose the website's public information
and public compute features through schemas for requests and markdown for
results.

Given feed, country, ASN, maintainer, search, category browsing, compose, and
custom address-space overlap pages share data with the website, when MCP output
is implemented, then it should be based on a reusable JSON-to-markdown
templating layer that can emulate the website pages without duplicating
business logic.

## Implications and decisions

### Design decisions (approved 2026-05-03)

**D1. Transport: Full Streamable HTTP** — single `/mcp` endpoint with POST
(JSON-RPC), GET (SSE notifications), session management via `Mcp-Session-Id`.
Full MCP spec (2025-03-26) compliance so all clients work out of the box.

**D2. Capability surface: Tools only** — no resources, no prompts. Two tools:

- `find_feeds(filters)` — discover feeds by metadata filters matching the
  homepage explorer: category, maintainer, provenance, health, freshness,
  cadence, uniqueness, license, redistributable, critical tier, size range.
  Returns a list of matching feeds with summary metadata.
- `fetch_analysis(type, name)` — fetch the full markdown analysis page for a
  specific entity. Type is one of `feed`, `country`, `asn`, `maintainer`. Name
  is the entity identifier (feed slug, two-letter country code, ASN number,
  maintainer slug). Returns the pre-generated markdown page from published
  artifacts.

Rationale: simpler than resources for LLM consumers — the model calls
`find_feeds` to discover, then `fetch_analysis` to get detail pages. Two tools
cover the entire public surface.

**D3. No resources or prompts** — follows from D2. Everything is a tool call.
The MCP resource list is empty; no prompts are registered.

**D4. No authentication** — same trust boundary as the public website. MCP
serves the same public data. No API key required. If abuse emerges, add
optional API key tier later.

**D5. Same rate limits as website** — 240 req/min for general API, 10 req/min
for search. No separate MCP limits. The `/mcp` endpoint shares the existing
`rateLimitMiddleware`.

**D6. Serve pre-generated artifacts** — `fetch_analysis` reads published
markdown from `{web-dir}/markdown/{type}/{id}.md` (generated by SOW-0085
pipeline). Zero compute, cache-first. `ExecuteInline()` used only if a tool
needs dynamic output in future SOWs (compose, address-space overlap).

**D7. Use `mcp-go` SDK** — `github.com/mark3labs/mcp-go` for protocol handling
(lifecycle, session management, SSE streaming, tool registration). Reduces
implementation to registering two tools and wiring them to existing data paths.

**D8. SOW-0013 ships first, without compose/overlap tools** — compose
(`SOW-0010`) and address-space overlap (`SOW-0011`) are follow-up SOWs. Their
MCP tools (`compose_feeds`, `check_address_space`) will be added later using
the same transport infrastructure.

**D9. Endpoint path: `/mcp`** — short, conventional for MCP servers. Not under
`/api/v1/` because it is a different protocol, not a REST API.

### Implications

- MCP must never expose admin operations or internal state.
- `find_feeds` needs access to published feed summaries (currently served via
  `GET /api/v1/sets`). The tool reads the same published artifacts.
- `fetch_analysis` reads published markdown from `pkg/markdown/` output dir
  (the SOW-0085 artifacts).
- The `mcp-go` server runs inside the existing Go HTTP server, mounted at
  `/mcp`, sharing the same listener and middleware stack.
- MCP is coupled to `SOW-0010` and `SOW-0011` for future compose and
  address-space overlap tools, but this SOW does not implement them.

## Pre-Implementation Gate

### Problem / Root Cause Model

No MCP endpoint exists. update-ipsets has a rich public website with feed
analysis, entity pages, search, and compose — but only as HTML/JSON. AI agents
and MCP-compatible tools (Claude Desktop, VS Code Copilot, Cursor, opencode)
cannot programmatically access this data. The MCP endpoint makes the entire
public surface available as two simple tool calls.

### Evidence Reviewed

- MCP Streamable HTTP spec (2025-03-26): POST for JSON-RPC, GET for SSE,
  session management via `Mcp-Session-Id` header.
- `github.com/mark3labs/mcp-go` v0.50.0: implements full Streamable HTTP
  transport, tool registration, session management, SSE streaming. Returns
  `http.Handler` for mounting on existing mux.
- Current public routes (`pkg/web/routes.go`): ~40 API endpoints, SPA fallback,
  rate limiting at 240/min general, 10/min search.
- Current middleware stack (`pkg/web/surface_handler.go:61`):
  log → cors → gzip → recover → rateLimit → mux.
- Published artifacts: feed JSON summaries at `{web-dir}/`, markdown pages at
  `{web-dir}/markdown/{type}/{id}.md` (SOW-0085).
- Go version: 1.26.1 (meets mcp-go requirement of 1.25.5+).

### Affected Contracts and Surfaces

- **New**: `pkg/mcp/` package — MCP server, tool handlers, wiring.
- **New**: `/mcp` HTTP endpoint on the public listener.
- **Modified**: `pkg/web/surface_handler.go` or `pkg/web/routes.go` — mount
  MCP handler.
- **Read-only**: `pkg/markdown/` — `fetch_analysis` reads published artifacts.
- **Read-only**: published feed summary artifacts — `find_feeds` reads them.
- **Read-only**: existing search infrastructure — `find_feeds` may reuse for
  IP lookup filter.
- **No changes**: admin routes, pipeline, config, entity artifacts.

### Existing Patterns to Reuse

- `mcp-go` SDK handles transport, session management, JSON-RPC, SSE streaming.
- Published artifact reading pattern from `pkg/web/` handlers: read file from
  configured web dir, return to client.
- Rate limiting via existing `rateLimitMiddleware` — MCP endpoint shares it.
- Feed summary data already published as JSON — `find_feeds` reads the same
  artifacts that `GET /api/v1/sets` serves.
- Markdown artifacts from SOW-0085 — `fetch_analysis` reads pre-generated files.

### Risk and Blast Radius

- **Risk**: MCP endpoint could be abused for heavy compute if tool handlers do
  expensive work. Mitigation: both tools are cache-first reads (pre-generated
  artifacts, published JSON summaries). No dynamic computation in this SOW.
- **Risk**: `mcp-go` is pre-v1 (v0.50.0). API may change. Mitigation: pin
  version in `go.mod`, abstract behind thin `pkg/mcp/` wrapper.
- **Risk**: `/mcp` endpoint could leak admin data if handlers access internal
  state. Mitigation: MCP package only receives read-only paths to published
  public artifacts, never the engine or admin interfaces.
- **Blast radius**: low. New endpoint, new package. No changes to existing
  public routes, pipeline, or admin. If MCP breaks, website still works.

### Sensitive Data Handling Plan

- No sensitive data in scope. MCP serves the same public data as the website.
- No credentials, no admin state, no internal metrics.
- Feed URLs in config may contain API keys in query params — `find_feeds` returns
  feed metadata (name, description, size, category), not source URLs.

## Lessons extracted

1. **Route prefix matters for middleware**: MCP at `/mcp` bypassed `/api/`
   prefix checks in rate limiting and CORS. When adding a new top-level route,
   audit all middleware that filters by path prefix.
2. **MCP tool descriptions are a product surface**: Tool and parameter
   descriptions are consumed by AI models. They need semantic context (what
   values mean, examples, use cases) not just technical labels. Treat them like
   API documentation for a non-human audience.
3. **`mcp-go` default annotations are wrong for read-only tools**: Default
   `readOnlyHint: false` and `destructiveHint: true`. Must explicitly set
   `readOnly()` for read-only tools so models know they're safe.
4. **Go 1.26 ServeMux pattern conflicts**: Registering `/mcp` (no method)
   conflicts with `GET /`. Must register per-method: `POST /mcp`, `GET /mcp`,
   `DELETE /mcp`.
5. **Distinguish metadata filtering from search**: `find_feeds` filters an
   in-memory slice of ~100 summaries (cheap, 240/min). IP search scans millions
   of entries (expensive, 10/min). Don't conflate the two when setting rate
   limits.

### Requirements

#### Purpose

Make the public, unauthenticated Streamable HTTP MCP endpoint usable by
browser-based MCP clients without weakening the admin CORS boundary.

#### User Request

The user reported CORS errors while trying to use MCP and stated that the MCP
server should be unprotected.

#### Assistant Understanding

Facts:

- The original approved design decision D4 in this SOW says `/mcp` has no
  authentication because it serves the same public data as the website.
- [pkg/web/http.go](../../pkg/web/http.go) advertises `/mcp` methods `GET`,
  `POST`, `DELETE`, and `OPTIONS`, but only advertises `Content-Type` in
  `Access-Control-Allow-Headers`.
- The MCP 2025-06-18 Streamable HTTP specification requires clients to send
  `Mcp-Session-Id` on subsequent requests after the server assigns it, and
  requires `MCP-Protocol-Version` on subsequent HTTP requests.
- The MCP specification also says stream resumption uses `Last-Event-ID` on
  GET requests.
- `mark3labs/mcp-go` v0.50.0 sends `Mcp-Session-Id` and
  `Mcp-Protocol-Version` through its Streamable HTTP client and reads
  `Mcp-Session-Id` in the server.

Inferences:

- Browser preflight fails because the server does not advertise the non-simple
  MCP request headers the client must send.
- `Mcp-Session-Id` should also be exposed to browser JavaScript so clients can
  read the server-assigned session header after initialization.

Unknowns:

- None blocking. The exact browser client was not provided, but the failing
  header class is dictated by the MCP transport and local `mcp-go` behavior.

#### Acceptance Criteria

- `/mcp` preflight responses allow `Content-Type`, `Mcp-Session-Id`,
  `MCP-Protocol-Version`, and `Last-Event-ID`.
- `/mcp` responses expose `Mcp-Session-Id` to browser clients.
- Non-MCP public CORS behavior remains unchanged.
- Admin paths still do not emit wildcard CORS headers.
- Specs and operator docs describe the actual MCP CORS contract.

## Regression - 2026-05-16 - find_feeds enum schemas

### Status

Status: completed

Sub-state: Regression fixed, validated, and ready to return to
`.agents/sow/done/`.

### Requirements

#### Purpose

Make `find_feeds` self-describing for MCP callers so they can discover valid
filter values from the tool schema instead of guessing from prose.

#### User Request

The user reported that `find_feeds` should provide enums for most fields. They
called out `cadence`, `category`, `critical`, `health`, `license`,
`maintainer`, `provenance`, and `redistributable` as fields that can and should
be enums because otherwise callers do not know what to put.

#### Assistant Understanding

Facts:

- `pkg/mcp/server.go` already uses `mcpgo.Enum(...)` for
  `fetch_analysis.type`.
- `find_feeds` currently defines `category`, `maintainer`, `provenance`,
  `health`, `freshness`, `cadence`, `uniqueness`, `license`,
  `redistributable`, and `critical` as plain strings.
- `mcp-go` v0.50.0 documents and implements `mcp.Enum(...)` for string tool
  parameters.
- Several `find_feeds` filter domains are fixed taxonomies:
  provenance, health, freshness, cadence, uniqueness, redistributable, and
  critical tier.
- `category`, `maintainer`, and `license` are catalog-derived values and must
  not be frozen in code as stale examples.

Inferences:

- Fixed taxonomies should use static enum lists backed by the same constants or
  bucket functions used by filtering.
- Catalog-derived values should be generated from the active public feed
  catalog when the MCP server is constructed.

Unknowns:

- Whether MCP clients refresh tool schemas after a daemon config reload. This
  implementation updates schema values on server construction; a full dynamic
  tool-list update on runtime reload is out of scope unless later evidence
  shows clients need it.

#### Acceptance Criteria

- `find_feeds` schema includes enum values for fixed filters:
  `provenance`, `health`, `freshness`, `cadence`, `uniqueness`,
  `redistributable`, and `critical`.
- `find_feeds` schema includes catalog-derived enum values for `category`,
  `maintainer`, and `license` when those values exist in the public feed
  catalog.
- Filtering behavior remains backward compatible for existing string inputs.
- Specs and operator docs describe enum-backed filters without implying stale
  hardcoded maintainer or license values.
- Tests prove the `find_feeds` tool schema exposes enums.

### Pre-Implementation Gate

Status: ready

Problem / root-cause model:

- The tool result handler can filter correctly, but the tool input schema does
  not communicate valid values to MCP callers. This forces callers to infer
  strings from descriptions, which is exactly what JSON Schema enums are for.

Evidence reviewed:

- `pkg/mcp/server.go`: `find_feeds` uses free-form `WithString` parameters;
  `fetch_analysis.type` already uses `mcpgo.Enum(...)`.
- `pkg/mcp/find_feeds.go`: filter matching expects exact values for most
  fields and substring matching for maintainer.
- `pkg/mcp/engine_catalog.go`: public feed summaries already expose category,
  maintainer, license, provenance, health, freshness, cadence, uniqueness, and
  critical tier data used by `find_feeds`.

  recomputation.

  term to match somewhere in the concatenated name, maintainer, and info text.
- Maintainer and info should move out of the compact table because those fields
  are long or prose-heavy.
- Date fields come from existing public summary Unix-second timestamps; only MCP
  rendering changes.
