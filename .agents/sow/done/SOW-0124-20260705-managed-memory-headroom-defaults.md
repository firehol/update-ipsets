# SOW-0124 - Managed Memory Headroom Defaults

## Status

Status: completed

## Requirements

### Purpose

Stabilize managed daemon installs under production entity-refresh memory pressure by giving the Go runtime, systemd memory pressure line, and systemd hard kill limit separate headroom bands.

### User Request

The user approved changing the managed install defaults to:

- `MemoryMax=3G`
- `MemoryHigh=2.5G`
- `GOMEMLIMIT=2GiB`

### Assistant Understanding

Facts:

- The current managed unit uses `MemoryHigh=1536M`, `MemoryMax=2G`, and `GOMEMLIMIT=1536MiB`.
- Production cgroup memory events showed repeated `memory.high` pressure without kernel OOM kills.
- The Go runtime memory limit does not include all memory charged to the service cgroup.
- Go rejects `GOMEMLIMIT=2G`; the valid spelling is `2GiB` or `2048MiB`.

Inference:

- Coupling `GOMEMLIMIT` to `MemoryHigh` leaves too little headroom for non-Go memory, kernel memory, mmap/file-backed reads, file cache pressure, stacks, and transient allocator behavior.
- The approved defaults create three bands: Go target at 2GiB, kernel pressure at 2.5G, hard kill at 3G.

### Acceptance Criteria

- `install.sh` writes the managed unit with `MemoryHigh=2.5G`, `MemoryMax=3G`, and `GOMEMLIMIT=2GiB`.
- Operator docs and runtime docs describe the new defaults.
- The memory-management spec records that `GOMEMLIMIT` is intentionally lower than `MemoryHigh`.
- Project operations skill records the new managed install defaults.
- Validation proves the installer script syntax and systemd unit memory syntax are accepted.

## Pre-Implementation Gate

Status: ready

Problem / root-cause model:

- Managed installs previously set the Go soft memory target at the same effective level as the cgroup pressure threshold.
- Because Go's soft limit excludes some process and kernel memory, the cgroup can enter reclaim/throttle before the Go runtime has enough practical headroom.
- Under large entity refreshes this can contribute to watchdog starvation and slow progress even without an OOM kill.

Evidence reviewed:

- `install.sh` resource limits.
- `.agents/sow/specs/memory-management.md` managed service memory guardrail.
- Operator docs under `docs/installation/` and `docs/running/`.
- Local `go doc runtime/debug.SetMemoryLimit`.
- Local check that `GOMEMLIMIT=2G` fails and `GOMEMLIMIT=2GiB` works.
- Local `systemd-analyze verify` check that `MemoryHigh=2.5G` and `MemoryMax=3G` are accepted in a unit file.

Affected contracts and surfaces:

- Managed systemd unit generated by `install.sh`.
- Operator documentation for installed defaults and memory planning.
- Runtime environment variable reference.
- Project memory-management spec.
- Project operations skill facts.

Existing patterns to reuse:

- Existing installed-unit resource-limit block in `install.sh`.
- Existing docs sections that already list managed install defaults.
- Existing spec section "Managed service memory guardrail".

Risk and blast radius:

- Managed installs reserve more memory by default, which may be unsuitable for very small hosts.
- Existing custom systemd drop-ins continue to override these values.
- Larger limits reduce cgroup throttling risk but do not remove the need for bounded algorithms and streaming writers.
